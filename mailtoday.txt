During the additional review, we observed that when the Application ID becomes available and is pushed into the data layer, the same Application ID is also being persisted in localStorage. Based on this, we were considering whether the existing eVar16 retrieval approach could be simplified and made more reliable.
Currently, some of the data elements search through the digitalData history to identify the most recent analyticsID. As discussed, relying only on reverse iteration of the data layer may not always be reliable, particularly when the Application ID is not present in every event or has not yet been pushed at the time an Analytics rule executes.
One possible approach would be to create a single standardized Application ID data element with the following logic:
Retrieve the latest valid Application ID from the current data-layer/state where available.
If the Application ID is unavailable there, use the persisted Application ID from localStorage as a fallback.
Normalize the returned value so that, whether analyticsID is supplied as a string or an object, the data element always returns only the actual Application ID as a string.
Using the current data-layer value first would help ensure that the most recent Application ID is used, while localStorage could provide persistence for subsequent events where the ID is no longer explicitly available in the data layer.
This could also address the [object Object] issue we identified. Instead of maintaining multiple Application ID data elements with slightly different return logic, all eVar16 mappings could eventually reference the same standardized data element, ensuring that an object is never passed directly into Adobe Analytics.
Conceptually, the flow would be:
Current Application ID → LocalStorage fallback → Normalize value → eVar16
This should provide a more consistent Application ID across the journey and remove the difference in behaviour between the existing data elements.
